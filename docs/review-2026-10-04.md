# 牵丝 产品审查报告

日期：2026-10-04
范围：整体业务逻辑、11 个菜单的实现与交互、6 类数据的添加流程；对标 personal CRM（Monica / Dex / Clay / folk）与中文「人情账簿 · 随礼记账」类 App
方法：源码走查（`internal/{api,store,db,notify,lunar,backup}` 约 16.3k 行 Go + `web/src` 约 4.8k 行 Svelte 5）+ 路由清单与前端调用比对 + 同类功能检索

> 本报告取代 [review-2026-09-29-product-audit.md](./review-2026-09-29-product-audit.md)。旧报告里的 4 个 P0 与大部分 P1/P2 已在 `c222da8` 及之后的提交中修掉（金额单位、聚合 SQL、鉴权、CORS、编辑能力、还款流水、圈子多对多、主题、备份），请勿再据其判断现状。

优先级定义：

- **P0** 功能阻断或数据计算错误，必须立即修
- **P1** 主要功能坏掉或高危，影响正常使用
- **P2** 明显难用、口径不一致、可维护性问题
- **P3** 打磨项

## 0. 总体判断

**结论：产品骨架已经成型且明显优于国内同类的开源实现，但「最后一公里」的接线问题很多——功能都在，偏偏在最需要它的部署形态（令牌 + 手机 + 长期无人值守）下失效。**

已经做对的（不需要再动）：

- 领域建模准确：金额存分、农历独立成包并有 `NextOccurrence` 年循环、事件与账本通过 `transactions.event_id` 打通且「删事件只解绑不删账」、引荐链有环检测与存在性校验（`internal/api/people.go:91`）、生日↔纪念日双向同步闭环、圈子改多对多后图谱按圈子拼色。
- 「以我为中心」的产品判断落地了：`settings.self_person_id` 指针 + 所有选人下拉把本人置顶 + 关系图按「离我几步」做同心放射布局（`web/src/lib/graphLayout.ts:19`）。这是同类产品里少见的正确押注。
- 数据安全意识在：`VACUUM INTO` 一致性快照、恢复前先归档 + 探针校验 + 补迁移、常数时间令牌比较、CORS 默认关闭、uploads 路径清洗。

三个系统性短板（贯穿下面所有条目）：

1. **口径不自洽**：同一个「欠账」在不同地方算出不同的数；承诺到期既不进待办也不进推送。
2. **失败不响**：约三分之一的写操作没有错误分支，叠加令牌模式后另有三类下载/图片入口失效。
3. **单用户桌面假设过头**：现场录入（酒席、路边）与长期无人值守（自动备份、每日摘要）是这类产品真正的两个使用时刻，恰恰都缺。

## 1. 新增数据流程现状

| 路径 | 入口 | 校验 | 结论 |
|---|---|---|---|
| 联系人 | 人物页弹窗 / vCard 导入 | 姓名（前后端均有）+ 重名实时提示 | ✅ 完整（圈子、标签、自定义字段、引荐人、头像、关系齐备） |
| 往来事件 | 往来页 / 详情页时间线（模板预填、参与人可搜索） | 标题 + 日期，开销需参与人 | ⚠️ 可用，但**礼物/礼金没有金额字段** |
| 对话/承诺 | 对话页 + 详情页「记一句话」 | 内容 | ⚠️ 可用，但**到期日不进待办、不进推送** |
| 金钱 | 金钱页 + 详情页「记一笔钱」 | 联系人 + 金额 > 0 | ❌ 快捷入口写死 `kind=loan, direction=out`（`web/src/pages/PersonDetail.svelte:155`）；非借还类不勾「已结清」会被算成欠款 |
| 纪念日 | 纪念日页 | 标题 + 日期 | ⚠️ `remind_days` 是裸文本框，无校验 |
| 待办 | 待办页 | 标题 + 日期 | ⚠️ 时间固定 09:00，不能设提前量/重复 |
| 关系 / 引荐链 | 详情页关系区、关系图添加（含多跳链一次录入） | 自环、空类型 | ✅ 有入口；但链上「当场新建的人」不查重、失败不回滚 |
| 标签 | 人物表单 + 设置页维护 | 名称唯一 | ✅ 已接通（旧审查的「零入口」已修） |

8 条路径全部有入口，这是相对 9/29 最大的进步。剩下的问题是语义与闭环，不是缺失。

## 4. 建议新增的功能

先厘清两件事：

- 同类产品（Monica / Dex / Clay / folk，以及国内的人情账簿、份子钱记账-人情礼金簿）的**基本盘**是：统一交互时间线、查重与合并、多条件搜索、**CSV/Excel 明细导出**、**移动端现场录入**、**外部通知通道**。牵丝已具备时间线（`/api/v1/people/{id}/timeline`）、查重合并（`/people/duplicates`、`/people/{id}/merge`）、apprise 多通道出站；后三项缺。
- **中文随礼场景特有、国际 personal CRM 普遍没有的**：**按联系人汇总的人情差值**、**回礼金额建议**、**事由（婚/满月/寿/白事）模板与宴席名单**、**单场盈亏对账**、**金额忌讳校验**。牵丝在这五项上全空。

| # | 功能 | 解决什么用户任务 | 优先级 |
|---|---|---|---|
| N1 | **按人的往来净额与回礼对照**：详情页与人物卡显示「我随出去 X、收到 Y、净额 Z、最近一次接触」。后端目前只有全局按方向的净额（`internal/store/events.go:1024`），无按人聚合 | 「老王儿子结婚随了 800，我该回多少」——这是随礼场景约 80% 的打开理由 | P1 |
| N2 | **礼金/礼物金额与事件绑定**：`events` 只有 `has_gift` + `gift` 文本（迁移 003），`EventForm` 只能生成 `kind=expense` 的开销。补 `gift_amount_fen` + 方向，保存时自动生成 `kind=gift` 账目并挂 `event_id` | 婚礼/寿宴现场记完事就结账，不用再去金钱页二次录入并手动选关联事件 | P1 |
| N3 | **结构化导入导出**：事件/对话/金钱的 CSV·Excel 明细导出（支持按年、按人）+ 全量 JSON 导出/导入。vCard 只覆盖通讯录 | ① 数据迁移不再被锁定（现在换机只能拷 `.db`）② 把某场宴席的礼单导给配偶/管事对账 | P1 |
| N4 | **PWA + 现场快速录入**：manifest + 离线缓存 + 主屏图标；一个「三秒记一笔」的全屏浮层（人 + 事由 + 金额，离线排队后补传） | 酒席上、送客时是唯一的真实录入时机，纯桌面 Web 直接失效 | P1 |
| N5 | **跟进节奏引擎（配置化）**：现在「久未联系」是写死阈值的一条建议文案（`internal/api/suggest.go:32`）。改为按亲密度分级设「多久该联系」，逾期自动派生待办、进每日推送，并给出「渐远名单」页 | 从「今天提示我一下」升级为「这件事变成一件待办并真的推到我手机上」 | P2 |
| N6 | **事由/宴席模板 + 名单**：婚宴、满月、寿宴、乔迁、白事的预置模板（默认事件类型、默认提醒、默认随礼金额区间），一场事件带名单/桌次/经手人 | 中文场景的差异化能力；把事件从「一条记录」变成「一次可运营的活动」 | P2 |
| N7 | **附件落到业务实体**：`attachments` 已支持 `entity_type/entity_id`（001），但除头像外无任何 UI，也没有 list 接口。补往来照片、聊天截图、票据存证 | 「当时的合影」「他说还了的那张转账截图」是人情纠纷的唯一凭证 | P2 |
| N8 | **回收站 / 软删除 + 撤销**：全实体软删 + 保留 30 天 + 一键撤销；批量操作后给 5 秒 undo | 把 M9 + O5 的高危面从「不可逆」变成「可逆」 | P2 |
| N9 | **看板增强**：圈子分布、随礼净流入/流出趋势、承诺兑现率、Top 疏远 / Top 亲密名单、生日年历视图 | 从「我记了多少条」变成「我的人际关系现在怎么样」 | P2 |
| N10 | **微信/通讯录导入通道**：CSV/Excel 列映射导入（现在的 vCard 要求用户先从系统通讯录导出） | 降低首次录入成本，也是 N3 的镜像能力 | P2 |
| N11 | **自然语言快录**：一句话 → 「下周三和张三吃饭 AA 300」。**注意：`internal/api/nlp.go` 只是供词云用的 bigram 词频分词，不是输入解析，也没有生产调用** | 把录入成本压到一句话，移动端尤其需要 | P3 |
| N12 | **忌讳与礼仪校验**：金额含 4 提示、单双数规则（白事单、喜事双）、超出行情的随礼提醒 | 中文场景独有的「懂行」体验，成本低辨识度高 | P3 |
| N13 | **通知历史可查**：`notification_logs` 表已建但生产代码从不写入，设置页看不到「推过什么、成没成」 | 排障与信任：M3 这类「没收到推送」目前无从自证 | P3 |
| N14 | **AI 会前简报**：见某人前生成关系摘要 + 未兑现承诺 + 上次话题 + 建议金额（词云、时间线、账本数据都已在库） | 差异化亮点，但依赖 N1/N2/N4 先落地 | P3 |

## 5. 落地顺序（粗估，按 1 人全职、含测试）

| 批次 | 内容 | 预估 | 判据 |
|---|---|---|---|
| ① 口径与无人值守 | M1 债务口径按 `kind` 过滤、M2 恢复后重建调度器、M3 通知改「到点必触发」、M4 承诺进待办与推送 | 3–4 天 | 四条都是「数字不可信 / 数据会丢 / 提醒不来」，是产品信任的地基 |
| ② 令牌与移动端可用 | M5 下载与图片走带令牌通道（或签名 query）、M6 移动端搜索入口 + N4 的 PWA manifest | 3–4 天 | 决定 README 推荐的部署方式是否真的可用 |
| ③ 数据完整性 | M7 写 0 行回 404 + 事件开销同事务 + `event_id` 外键、M8 上传白名单与大小上限、M10 入参校验、M9 危险操作确认强化（软删见 N8） | 4–5 天 | M8 是唯一的安全项，放这批前段 |
| ④ 场景核心能力 | N1 按人净额、N2 礼金绑定事件、N3 CSV/JSON 导入导出 | 5–7 天 | 补齐与中文同类的基本盘差距，成本最低收益最高 |
| ⑤ 体验与规模 | O1/O2 请求收敛与异步选人、O3 统一错误提示（含 O5 toast/undo）、O6 筛选维度、O8 首启引导与本人入口、N5 跟进节奏 | 5–7 天 | 可按用户实际反馈插队 |
| ⑥ 亮点 | N6 事由模板（建议先做最小版：模板 + 名单）、N7 附件、N9 看板、N12 忌讳校验、N11/N14 AI | 待评估 | 依赖 ④ 的数据结构先到位 |

**回归防护（建议与 ① 同批做）**：目前后端有 179 个测试函数、覆盖率门槛 80%，但前端**零测试**（`web/package.json` 只有 `svelte-check`），`.github/workflows/` 也只剩 `ci.yml`。旧审查里那类「编译不报错、CI 不拦截、功能实际是坏的」缺陷（当时的 M1 新建按钮）至今没有防线。至少补一组关键路径冒烟：新建对话 → 记一笔礼物 → 检查首页「我借出」是否虚增 → 从备份恢复后跑一次自动备份。这四步能同时锁住 ① 批次的全部四条。
